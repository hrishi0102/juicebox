# Friction log

What slowed us down while building on Arkiv, in the order we hit it. Written so the Arkiv team can fix things, not to complain.

1. **Old tutorials no longer work.** SDK 1.0 (Oct 30, 2026) is a breaking rewrite: no more `payload` and `annotations` fields, no `expiresIn`, no `updateEntity`. Most examples found by search (and by AI assistants) still show the 0.x API. A short "migrating from 0.x" page at the top of the docs would save everyone time.
2. **The query syntax changed silently.** `type = "receipt" && team = "x"` now fails with `-32001 unexpected character`. The new form is `type = str('receipt') AND team = str('x')`. The error message could say "values need a type, for example str('x')".
3. **`llms.txt` is partly out of date.** It still lists `ne`, `not`, cursors and `atBlock`, which 1.0.1 does not export. Since many builders now read docs through AI tools, this file matters a lot.
4. **Faucet sign-in is heavy for a hackathon.** Getting tGLM needs a wallet connection, a sign-in signature, an email registration and a CAPTCHA per claim, with a 24 hour cooldown. Because every wallet that writes needs gas, an app cannot let each user write their own entity without sending every user through that flow. We worked around it with one writer wallet and EIP-712 signatures inside the payload, so authorship does not depend on who paid the gas. A sponsored-write option (a paymaster, or "writer pays for another signer") would make user-owned entities practical.
5. **Bigints need wrapping.** Numeric attributes default to `i32`; a `u64` value must be wrapped (`u64(123n)`). Easy once known, but the type error is long. A one-line example in the schema docs would help.
6. **Public RPC warning.** Without an access key the SDK prints a rate-limit warning on every client. Fine, but getting a key needs the same Hub sign-in as the faucet.
7. **Misleading error for an empty wallet.** With no tGLM, `createEntity` throws `EntityMutationError: Transaction failed: Execution error without revert data`. The real cause (`insufficient funds for gas * price + value: have 0 want 1240650000000000`) is five levels down the `cause` chain. Surfacing the innermost RPC message (or an `InsufficientFundsError`) at the top would save a lot of head scratching. We now walk the chain ourselves (`explainArkivError`). Related: the SDK first calls `eth_fillTransaction`, which the Rabdi RPC does not support (`-32601`); it falls back fine, but it is noise in logs.
8. **No "owned by signer" concept.** `$owner` is whoever paid for the write. We now work around it by creating the entity read-only and handing ownership to the signer in the same batch (`predictEntityKeys` + `executeBatch`), which works well. A verified "author" field (for example an EIP-712 signature checked by the node) would still save every reader from re-verifying payload signatures.
9. **String attributes stop at 128 bytes, and the error only shows at write time.** We stored a sealed pointer (about 200 bytes) in a `str` attribute and only learned of the limit by reading the SDK source (`MAX_STRING_BYTES = 128`). It now lives in a `bytes` attribute. Stating the limit in the schema docs, or failing at `defineSchema` time for obviously long values, would save a round trip.
10. **Anonymous queries are refused, so a README query cannot be run as is.** Without an access key, even one small `arkiv_query` returns `ANON_COST_LIMITED`, every time (we retried after a pause). The prize asks for "one query judges can run", but a judge copying it into curl gets that bare code and no hint. A short message ("anonymous queries are limited; get a free key at hub.arkiv.network/access-keys and put it at the end of the RPC URL") would turn a dead end into one step. We now print the ready-to-run command with an `<ACCESS_KEY>` slot in our README.
11. **The access key goes in the URL path, which is easy to miss.** It is the last path segment of the RPC address (`https://rpc.rabdi.db-chain.testnet.arkiv.network/<key>`), not a header. The SDK hides this (`rabdi({ accessKey })`), but anyone calling JSON-RPC directly (our Chainlink CRE job, a judge with curl) has to read the SDK source to find out.
12. **Read-only entities have no "replaced by".** We create receipts read-only on purpose, so a week sent again is a new entity, and every reader must work out which one is current. `$createdAt` makes that possible (we keep the latest per person and week), but a way to mark an entity as replaced by another, without being able to edit it, would save every reader the same logic.

What worked well: gas estimation tells you early whether an entity is valid (our full receipt with 11 attributes and a 3.5 KB payload estimated at about 827k gas, roughly 0.0012 tGLM), typed schemas with `defineSchema` are clear, the query builder is pleasant, expiry is simple, and the Rabdi testnet was up and fast whenever we tried it. The system fields are great: `$owner`, `$creator`, `$createdAt`, `$expiresAt` and `$creationFlags` let our public receipt page show, straight from the chain, that a receipt is read-only, owned by the person who signed it, written by a wallet that only paid the fee, and when it expires. The read-only flag doing exactly what it says (contents frozen, but the owner can still extend, transfer or delete) fits evidence perfectly.
